## 0. How to use this document (read first)

These rules apply to anyone building from this document, including AI coding assistants.

1. **Use only what is written here.** Screens, rules, fields, thresholds and AI prompts' inputs are defined in this file or in the linked module specs.
2. **Never invent medical content, numbers or rules.** Ranges come from the model training data files; formulas and wording come from the sources listed.
3. **Tags:** `[CONFIGURABLE]` = a setting in `config.yaml`; `[OPEN]` = not decided, leave a placeholder; `[CONFIRM AT REVIEW]` = a doctor must confirm before release.
4. **Patient-facing and doctor-facing fixed wording** is defined by message keys only. Final text lives in `messages.yaml`, doctor-approved.
5. **Linked module specs win** for their own rules (genetic rules, symptom rules, journey content). This document only defines how the dashboard shows and acts on them.

## 1. Purpose and scope

### 1.1 What the dashboard does
The doctor-facing web app. A doctor sees only her or his assigned patients, enters clinical data (CTG values, maternal vitals), sees AI predictions with explanations, reviews patient-entered data (symptoms, genetic answers), manages records, notes and appointments, and decides what the patient sees. A small admin area manages accounts and assignments.

### 1.2 Principles
- **Human in the loop:** AI and rules support; the doctor decides. Every AI output is labelled as decision support or as an AI draft.
- **Separate results:** fetal, maternal and genetic results are always shown separately. **No combined risk score.**
- **All access through FastAPI**, with role and assignment checks on every request (TRD §5).

### 1.3 What it never does
- Never shows a combined or weighted overall risk score.
- Never lets anyone type or override a prediction, a probability or a genetic percentage.
- Never sends an AI draft to a patient without a doctor approving it.
- Never shows a patient's data to a doctor who is not assigned to that patient.
- Never shows clinical data to the admin role.

## 2. Glossary

| Term | Meaning |
|---|---|
| **assigned doctor** | A doctor linked to the patient in `doctor_patient_assignments`. A patient can have several. |

| **AI draft** | Text generated by the LLM for a doctor to edit and approve (section 18). |
| **model units** | The units each model was trained on (section 9.3). |

## 6. Patient list

**Columns:** name, gestational age (weeks + days), due date, latest fetal class, latest maternal class, genetic status, latest symptom level, unseen inbox count, pregnancy status.

**Default order:**
1. Patients with an unseen inbox item of type `symptom_l1` or `chat_urgent`.
2. Patients with an unseen `symptom_l2`, `pattern_p5` or `genetic_high_priority` item.
3. Patients with any other unseen item.
4. Everyone else, by name.

Within each group, newest item first. Search by name; filters by status columns.

Classes are shown as the model labels (`Normal` / `Suspect` / `Pathological`; `Low` / `Mid` / `High`) with the date of the reading. Colour may help scanning but the text label is always present.

## 8. Patient records and linking

### 8.1 Create and edit
A doctor creates a patient record (name, optional age and notes). The creating doctor is assigned automatically and becomes primary if no primary exists. Other doctors are added by the admin (section 21).

### 8.2 Invite link
1. The doctor clicks "Invite patient". The backend creates a random one-time code (`invite_code_length`, default 8 characters, no ambiguous characters) that expires after `invite_code_days` (default 7) `[CONFIGURABLE]`, and returns an **invite link** `<patient-app-url>/join?code=<code>` (DEC-024).
2. The doctor copies the link and sends it to the patient outside the app. Creating a new link cancels any unused earlier link for that patient.
3. Patients can sign up **only** through a valid invite link (no open sign-up). After sign-up, the backend sets `patients.user_id` and marks the code used.
4. Invalid, used or expired codes are rejected with no detail about which. A record that already has a `user_id` cannot get a new code.

### 8.3 Pregnancy dates
Doctors can set a `clinician_confirmed` or `ultrasound` due date (Module 4 §5). The change is logged and the patient gets a `dates_updated` notification.

## 9. Clinical data entry and predictions

### 9.1 Forms
- **Fetal:** the 21 CTG features, grouped as in the test frontend (for example Baseline & Variability, Histogram Statistics). Field list and order come from `fetal_risk_feature_order.json` (via `GET /schema/fetal`), never hard-coded.
- **Maternal:** the 8 inputs (age, systolic BP, diastolic BP, body temperature, heart rate, BMI, HbA1c, fasting glucose), from `maternal_risk_feature_order.json`.

### 9.2 What happens on submit
1. Validate the input types.
2. Convert units to model units (section 9.3).
3. Check training ranges (section 9.4).
4. Call the existing prediction endpoint.
5. Save an append-only row in `fetal_results` / `maternal_results` with inputs (model units), entered values and units, prediction, confidence, class probabilities, top contributing factors, `entered_by`, `model_version`, and range warnings.

### 9.3 Units (maternal model)

| Input | Model unit | Other unit accepted | Conversion | Source |
|---|---|---|---|---|
| HbA1c | mmol/mol | % (NGSP) | mmol/mol = 10.93 × % − 23.50 | S1 |
| Fasting glucose | mmol/L | mg/dL | mmol/L = mg/dL ÷ 18 | S2 |
| Body temperature | °F | °C | °F = °C × 9/5 + 32 | standard |

- Each unit field has a visible unit switch. The default unit is `[CONFIGURABLE]` (`default_units`) and should match local lab reports `[CONFIRM AT REVIEW]` (U1).
- The converted value is shown next to the entered value before submit ("7.0 % = 53 mmol/mol").
- Both the entered value + unit and the converted value are stored.
- Conversion formulas `[CONFIRM AT REVIEW]` (U2).

### 9.4 Training-range warnings
- A one-time script computes the minimum and maximum of every feature from each model's cleaned training data and saves them as `fetal_risk_feature_ranges.json` and `maternal_risk_feature_ranges.json` next to the model files. **No range is typed by hand.**
- Any value outside its range shows `warn_outside_training_range` next to the field and next to the prediction. The prediction still runs and the warning is stored with the result.

### 9.5 HbA1c and haemoglobin variants
If the patient's latest genetic assessment shows a haemoglobin-group status other than `tested_negative` or `unknown` for the mother, show `note_hba1c_haemoglobin_variant` beside the HbA1c field and the maternal result. HbA1c can be unreliable with haemoglobin variants (S3) `[CONFIRM AT REVIEW]` (U3).

### 9.6 Model limitations (shown beside every prediction)

| Key | Shown with | Intent |
|---|---|---|
| `lim_decision_support` | Fetal, maternal | AI decision support, not a diagnosis |
| `lim_public_data` | Fetal, maternal | Trained on public datasets; not validated on Alovia's patients |
| `lim_fetal_ctg` | Fetal | Requires computerised CTG analysis values (SisPorto-style) |
| `lim_maternal_separable` | Maternal | Test scores are near the dataset's ceiling and do not indicate real-world accuracy |

### 9.7 Display of a prediction
Predicted class, confidence, bar chart of class probabilities, table of top contributing factors (feature, impact, direction relative to the predicted class), range warnings, limitations, model version, entered by, date. The SHAP direction wording follows the fixed backend (context_v2 §4, bug #2).

## 10. Sharing a result with the patient

1. Each fetal and maternal result starts **not shared**. The patient sees nothing about it.
2. The doctor clicks "Share with patient" and sees the patient view preview:
   - the class in plain words with doctor-approved template text for that class (`result_template_{model}_{class}`, 6 templates);
   - an optional doctor message (typed, or an AI-2 draft edited by the doctor).
3. On confirm, a row is saved in `result_shares`; the patient gets a `result_available` notification (Module 4 §10).
4. The patient never sees probabilities, confidence values or SHAP factors.
5. A share cannot be undone; a later note can add context.

## 18. AI features

### 18.1 Common rules (apply to AI-1 … AI-4)
1. **AI drafts, doctor approves.** Nothing generated by the LLM reaches a patient without a doctor editing or approving it. AI-1 and AI-4 are doctor-only and never reach patients.
2. **Structured input only.** Code builds the input from stored data. The LLM never queries the database.
3. **No identifiers.** Names, phone numbers, emails and IDs are never sent; the patient is "the patient".
4. **No new facts.** Prompts instruct the model to use only the given facts. Code checks that every number in the output appears in the input; if not, the draft is discarded and the fallback (per feature) is shown.
5. **Labelled.** Every output shows "AI draft" or "AI suggestion".
6. **Logged.** Every call stores input, output, model name, prompt version and the doctor's action in `ai_drafts`.
7. **Flags.** Each feature has its own flag in `config.yaml`, default `false` until the LLM is chosen.
8. **Real patient data** may be sent only after a provider meeting the applicable privacy requirements is chosen or data is de-identified `[OPEN]`. Until then, only synthetic or test data is used.
9. **Failure.** If the LLM fails or times out (`ai_timeout_seconds`, default 15), show the fallback; the workflow never blocks on AI.

### 18.2 AI-1 — "Since last visit" summary
- **Where:** Patient Overview tab, doctor only.
- **Input (built by code):** a list of facts since the doctor last opened this patient (or the last `ai_summary_days`, default 14): check-ins with levels and symptom names, pattern changes, latest PUQE band changes, new fetal/maternal results (class, date), genetic status changes, new records, pregnancy status changes. Each fact has a reference.
- **Output:** 3–5 short sentences; each sentence links to the references it used.
- **Fallback:** the code-built fact list as bullets.

### 18.3 AI-2 — Draft message when sharing a result
- **Where:** Share dialog (section 10).
- **Input:** model (`fetal` / `maternal`), predicted class, the doctor-approved class template text, and the top contributing factor names translated with `feature_plain_names.yaml` (doctor-approved plain names, e.g. `ASTV` → "short-term heart-rate variability").
- **Output:** a short, plain-language message (max 120 words) placed in the editable message box.
- **Rules:** no numbers, no probabilities, no diagnosis, no treatment advice.
- **Fallback:** an empty message box.

### 18.4 AI-3 — Draft genetic counselling note
- **Where:** Genetic review (Module 3 §10.3).
- **Input:** per condition: rule ID, status, outcomes as stored, warnings and note keys with their approved text; consanguinity and timing flags.
- **Output:** a draft doctor note (max 150 words) in the note box.
- **Rules:** may only restate given outcomes; must recommend counselling when risk is indicated; no new percentages.
- **Fallback:** an empty note box.

### 18.5 AI-4 — Symptom note highlighter (doctor side only)
- **Where:** runs when a check-in with notes is saved (if enabled).
- **Input:** the note text only.
- **Output:** `flag: true/false` and a short reason (max 20 words).
- **Effect:** `true` creates an `ai_note_flag` inbox item (section 7). It never changes the check-in's red-flag level and never shows anything to the patient.
- **Label:** "AI suggestion — may miss things; red-flag rules are unchanged."
- **Fallback:** no flag.

## 25. Tests (all must pass before release)

1. A doctor cannot read or write data of a patient she or he is not assigned to (every endpoint).
2. Admin endpoints reject doctors and patients; admin cannot read clinical values.
3. Patient list ordering follows section 6 with mixed inbox items.
4. "Seen" by one doctor is visible to another assigned doctor.
5. Unit conversion: HbA1c 7.0 % → 53 mmol/mol (rounded), glucose 90 mg/dL → 5.0 mmol/L, 37 °C → 98.6 °F; entered and converted values both stored.
6. A value outside the training range shows the warning and stores it; the prediction still runs.
7. Haemoglobin-variant note appears only when the genetic status condition in section 9.5 holds.
8. A result is invisible to the patient before sharing and visible (template + message only) after.
9. Invite links: a valid link allows one sign-up and links once; used, expired and wrong codes fail with the same message; no sign-up form without a valid link.
10. Genetic review race: the second doctor's action is rejected.
11. Appointments: doctor cannot edit a patient-created appointment and vice versa.
12. AI: with flags off, no LLM call is made; output containing a number not in the input is discarded and the fallback shown; LLM failure shows the fallback; no names or IDs appear in logged inputs; AI-4 never changes a check-in level.
13. Rule review: with `require_signoff = true`, an engine with an unchecked row refuses to start.
14. Removing the last assigned doctor is blocked.
15. No screen shows a combined risk score (manual check).

## 26. Out of scope (version 1) and Do not

**Out of scope:** combined risk score; reading values from uploaded reports (OCR); patient access to medical records; video consultation or chat between doctor and patient; translation of notes; multi-clinic (multi-tenant) separation; push notifications; doctor scheduling or availability management.

**Do not:**
- Do not show a combined or weighted risk score.
- Do not let anyone edit predictions, probabilities or genetic percentages.
- Do not send any AI output to a patient without doctor approval.
- Do not send names or identifiers to the LLM.
- Do not type training ranges or conversion constants anywhere except the files and table defined here.
- Do not show clinical data to admins.
- Do not delete results, notes, records, inbox items, shares, sign-offs or log entries.
